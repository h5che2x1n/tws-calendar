# TWS 官方行程订阅

`data/original.ics` 保存原始快照；`data/events.json` 维护人工整理及部分自动更新的行程；`data/history.json` 收录历史行程；`data/auto_events.json` 保存程序从日本官方日程识别的活动。历史来源保存在数据中，不显示在历史日历详情。原 UID 和生日重复规则继续保留。

GitHub Actions 每天北京时间 09:00 执行自动检查，并在 09:23 再检查一次，尽量弥补定时任务延迟或漏跑；手动触发或向 main 提交也会运行。程序检查日本官网当前和未来日程，自动识别格式明确、只有一场的电视、电台与部分现场演出；有明确地址时生成地图链接。对于已有数据中格式受支持的人气歌谣申惟 MC、音乐中心道勋 MC 和个人视频签售 Weverse 公告，程序重查官方开始时间。日本官网的新公告标题和已知日本官网／Weverse 公告正文变化也会被记录为待核查项。通过验证的更新写回仓库后由同一次工作流部署到原订阅网址，电脑不需要开机。工作流不能保证准时执行，Apple 日历也有刷新延迟。

程序还检查 SBSKPOP 官方 YouTube 频道近期普通视频的 TWS 预告，并只对《순간뽀짝 세상에 이런 아이돌이》中成员、单一播出日期和韩国时间均清楚的预告自动生成行程；频道作为观看入口，预告作为来源。已入历且使用同一预告的未来行程会重查时间，改期保留 UID；可疑、格式不明或可能重复的内容仅列入运行摘要待核查。只查看频道当前显示的近期视频，不能保证发现所有内容；Shorts、其他节目、频道更新过快或网站结构变化均可能漏查。YouTube 无法读取时，摘要会标明检查未完成，不会据此取消活动。

**覆盖范围并不完整。**目前程序不能自动发现 Weverse 新公告，不能自动解析 PLEDIS、X 的新公告，不能可靠解析图片、复杂多场行程、多数签售、取消或成员不明确的节目。日本官网新公告标题只用于发现候选，不能保证相关活动自动入历。复杂活动、与既有记录可能重复的条目等列入人工核查，不会因为未找到而当作取消；已导入的原始事件和人工整理的日本官网事件也不会自动改期。`source-review` 工件及 Actions 运行摘要列出待核查项目和来源限制，成功仅表示受支持部分的程序运行成功，不表示检查完所有官方来源。需要定期人工检查 Weverse、X、PLEDIS 和主办方通知，并将核实的新增或变更写入 `data/events.json`。检查进度和正文指纹保存在 `data/source_state.json` 中，用于漏跑后补查与发现变更；若一则日本新闻确认无需入历，可将其标题的 UTF-8 SHA-256 记入该文件 `resolved_news` 并从 `pending` 删除，标题变化后会重新提醒。

## 首次启用

仓库 Settings → Pages → Build and deployment → Source 选择 GitHub Actions。进入 Actions → Build and deploy calendar → Run workflow。检查任务成功后打开 `https://h5che2x1n.github.io/tws-calendar/tws.ics`，确认返回 VCALENDAR 文本而非 404。iPhone 日历 → 日历 → 添加日历 → 添加订阅日历，输入此网址。Apple 刷新有延迟，不能保证立即更新。取消的表现取决于订阅客户端；保留取消记录以利同步。

## 添加和修改

编辑 `data/events.json`，仅收录官方确认的信息。格式示例使用虚构数据，不是实际行程：

```json
[{"id":"example-stable-id","title":"虚构示例","status":"confirmed","sequence":0,"all_day":false,"start":"2030-01-01T20:00:00+09:00","end":"2030-01-01T21:00:00+09:00","updated_at":"2029-12-01T00:00:00Z","source_url":"https://example.org/notice","watch_url":"https://example.org/watch","description":"说明"}]
```

实际活动必须核实开始时间及偏移量；不可推测开始时刻。仅日期已确认但时刻待定时可用 `all_day: true`、`time_tbd: true` 表示日期占位；时刻公布后沿用同一个 id 改成定时事件，递增 sequence。结束时间确定则填写；有合理时长依据时可以估计，设置 `end_estimated: true`，日历会标明结束时间为估计；没有依据时省略 `end`。线上综艺有确定播出时间时设置 `remind_at_start: true`；实际提醒受 Apple 日历订阅和设备通知设置影响。全天日期使用 `YYYY-MM-DD`，结束是排他的次日日期。`location` 放线下场馆及已确认可直接观看或参与的链接，没有则留空；不把公告网址当成观看入口。`details` 简述活动和成员，非全员活动须注明确切成员；`source_url` 是官方通知，`watch_url` 是已核实的观看链接。不要写核验过程或内部维护说明。节目、打歌、MC、电台、综艺、演出和官方签售等均可收录，须有官方确认。每个活动分配唯一永久 id，改期沿用 id 并递增 sequence、更新 updated_at；取消时保留记录，不复用 id。提交后工作流发布。

持续时间超过 12 小时的定时活动在订阅日历中按全天显示；跨多天时覆盖实际涉及的日期，恰好在零点结束时不额外占用结束日。具体起止时间保留在数据及日历详情中，仍以有时区的原始时间保存；如果设有开始提醒，提醒对应原来的开始时刻。恰好 12 小时及没有明确结束时间的活动仍按原时间显示。原始导入快照按其北京时间显示日历日期。

来源：日本官网 https://tws-official.jp/schedule 、PLEDIS https://www.pledis.co.kr/ko/artist/detail/TWS/notice/ 。公告可能有图片或需要登录；人工核对并记录来源。

## 维护检查

GitHub 的定时工作流在公开仓库长期无活动时可能自动停用。每月至少检查一次 Actions 最近运行时间和结果，手动 Run workflow 验证；收到 GitHub 定时停用提醒时重新启用。启用 GitHub 的 Actions 失败通知并检查邮件设置；工作流不运行时不会产生失败邮件，需独立检查或外部监控。访问固定 ICS URL 检查部署是否新鲜。工作流使用仓库 `GITHUB_TOKEN` 的 contents 写权限提交验证通过的日历数据；如果分支保护禁止 Actions 直接提交、仓库限制写权限或推送时发生冲突，工作流会失败并保留上一版本，需检查 Actions 日志。测试使用虚构、内存内的事件，不写入生产日历。
# 默认时长

仅当已知具体开始时间而未提供结束时间时，生成器根据活动类型填入估计时长并在详情标注。已知官方结束时间或正片长度优先。允许设置 `duration_category`：`video_fansign` 60 分钟、`offline_fansign` 120 分钟、`year_end` 240 分钟、`music_bank` 90 分钟、`music_core` 80 分钟、`inkigayo` 70 分钟、`radio` 120 分钟、`variety` 60 分钟、`vlog_behind`（Vlog／幕后花絮）30 分钟。未标注时仅对可识别标题推断；无法分类和预录活动不推断。日期待定或只有日期的活动不补时间。线上签售为整场估计，不是每人的通话时间；电台按整档节目，已知成员片段时间时应使用片段实际时间。修改已发布活动时必须沿用 UID 并提高 sequence。



已重新检索但仍无法可靠补到具体时刻的历史条目，保留 `all_day: true` 和 `time_tbd: true`，设置 `hide_time_tbd_note: true` 后不在日历备注显示“具体时间未记录（日期占位）”。`time_reviewed_at` 和 `time_review_status` 仅供维护，不输出到日历；`no_verifiable_time` 表示本次没有取得可核实的时刻（包括来源读取受限），不等于官方确认从未公布。后续取得官方时刻应继续更新同一 UID，清除日期占位状态；新活动待公布时间的提示照常保留。
